# kaizen-dojo

「動く」を「安心して使える」に変える力を鍛える、ソフトウェア品質学習アプリ。

出題されるコードは、**すべてテストが通り、手元では正しく動いています**。
探すのはバグではなく、まだ表に出ていないリスクです。

## 何を鍛えるアプリか

AIがコードを書けるようになったいま、開発者の差は「書けること」から
「生成されたコードを審査して責任を持てること」へ移っています。
このアプリは、その審査力を5つのドメイン・計25問で訓練します。

| No | ドメイン | 主眼 |
|---|---|---|
| 01 | コードレビュー | N+1問題、エラーの握りつぶし、競合状態、スコープ外の変更が混ざったPR、AI生成PRのレビュー方針 |
| 02 | データベース設計 | 金額の型、非正規化タグ、UNIQUE制約の欠如、マスタ参照による履歴汚染、多対多スキーマ設計 |
| 03 | 認証・セキュリティ | 弱いハッシュ方式、認可漏れ（IDOR）、トークン保管場所、危険なデフォルト設定、SQLインジェクション |
| 04 | 自動テスト | モック過多なテスト、再現テスト先行、テストの優先順位、フレーキーテスト、境界値の網羅 |
| 05 | 公開前セルフレビュー | エラー詳細の露出、優先順位判断、破壊的マイグレーション、緩すぎるCORS設定、公開前チェックリスト |

四択15問・記述10問。記述式はAIが採点基準に照らして採点します。
25問のうち22問には模範解答（修正後の完全なコードと、変更理由）が付いています。
コードを伴わない判断系の3問（AI生成PRのレビュー方針／公開前の優先順位／テストを書く優先順位）は、
原則と採点基準だけを持ちます。

## セットアップ

```bash
npm install
cp .env.example .env.local     # ANTHROPIC_API_KEY を設定する
npm run dev                    # http://localhost:3000
```

記述式のAI採点を使わない場合、`ANTHROPIC_API_KEY` は未設定のままでも動きます
（採点ボタンを押すとエラーになり、「採点基準を見る」から自己採点モードに切り替わります）。

### 環境変数

| 変数 | 必須 | 既定値 | 説明 |
|---|---|---|---|
| `ANTHROPIC_API_KEY` | 記述式採点に必要 | — | **サーバー側のみ**で使う。`NEXT_PUBLIC_` を付けないこと |
| `ANTHROPIC_MODEL` | 任意 | `claude-opus-5` | 採点に使うモデル |
| `GRADE_RATE_LIMIT_PER_MINUTE` | 任意 | `6` | 採点APIの1分あたりの上限 |
| `GRADE_RATE_LIMIT_PER_HOUR` | 任意 | `60` | 採点APIの1時間あたりの上限 |

### コマンド

| コマンド | 内容 |
|---|---|
| `npm run dev` | 開発サーバー |
| `npm run build` / `npm start` | 本番ビルドと起動 |
| `npm test` | ユニットテスト（Node標準のテストランナー） |
| `npm run typecheck` | 型チェック |
| `npm run lint` | ESLint |

## デプロイ

### GitHub Pages（静的エクスポート・採点なし）

`main` に push すると `.github/workflows/deploy-pages.yml` が動き、GitHub Pages に自動デプロイされます
（リポジトリ設定の Settings → Pages → Build and deployment → Source を **GitHub Actions** にしておくこと。
初回はここだけ手動での有効化が必要）。

GitHub Pages は静的ホスティングのみで、`/api/grade` が必要とするサーバーは動かせません。
このワークフローは `src/app/api` を**CIのチェックアウト上でのみ**取り除いてから
`next build` を静的エクスポートモード（`NEXT_STATIC_EXPORT=true`）で実行します。
コミットされているソースは変更されないので、後述のVercelデプロイには影響しません。

採点ボタンは押すとAPIが存在せず失敗しますが、既存のエラーハンドリングにより
自動的に「採点基準を見る」自己採点モード（採点基準と模範解答の表示）にフォールバックします。
四択・記述の演習、進捗の保存（localStorage）は通常どおり動きます。

手動で試したい場合は Actions タブから `Deploy to GitHub Pages` を `workflow_dispatch` で実行できます。

### Vercel（採点つきのフル機能）

記述式のAI採点まで含めてデプロイするなら Vercel を使ってください。
このリポジトリを Import し、`ANTHROPIC_API_KEY` を環境変数に設定するだけで、
コードの変更なしにそのままデプロイできます（Next.js の App Router / API Routes をそのまま利用）。

```
src/
├── app/
│   ├── layout.tsx          フォント読み込みとメタデータ

├── data/
│   ├── domains.json        設問25問
│   ├── fixes.json          模範解答22件
```

## 設問データの追加・修正

`src/data/domains.json` と `src/data/fixes.json` を編集するだけで完結します。
コードの変更は要りません。

設問（共通）:

```jsonc
{
  "id": "rev-1",                       // 全体で一意。fixes.json のキーにもなる
  "type": "mcq",                       // "mcq" | "free"
  "severity": "Major",                 // "Critical" | "Major" | "Minor"
  "situation": "状況説明（前提）",
  "code": "対象コード（任意・複数行可）",
  "prompt": "設問文"
}
```

四択（`"type": "mcq"`）は `choices`（4択）・`answer`（正解のindex）・
`explanation`・`principle` を、記述式（`"type": "free"`）は `rubric`（採点基準の配列）を
追加で持ちます。

模範解答（`fixes.json`）は設問IDをキーにした辞書で、`lang`（`js` / `sql` / `bash`）・
`code`（修正後の完全なコード）・`notes`（変更点と、その理由）を持ちます。
該当データが無い設問では模範解答ブロックが表示されないだけで、演習は成立します。

形が壊れていれば読み込み時に例外になります（`src/data/validate.ts`）。
`npm test` でも同じ検証を回しているので、設問を足したらテストを実行してください。

文中の `` `identifier` `` はインラインコードとして等幅で描画されます。

## AI採点

```
ブラウザ ──POST /api/grade──▶ Next.js の API Route ──▶ Anthropic API
         ◀──── 採点結果JSON ───┘   （ここにだけAPIキーがある）
```

**APIキーはクライアントに一切露出しません。** ブラウザが叩くのは自前の
`/api/grade` だけで、`ANTHROPIC_API_KEY` はサーバー側プロセスの環境変数として
保持されます。

採点結果は構造化出力（`output_config.format` にZodスキーマを渡す）で受け取ります。
モデルの応答がスキーマに沿った形で返るため、コードフェンスの除去やJSONパースの
リトライといった後処理は不要です。

レート制限は `src/lib/rate-limit.ts` が短期（1分）と長期（1時間）の2つの窓で判定します。
単一プロセスのメモリ上で数える実装なので、複数インスタンスに水平分割する場合は
Redisなどの共有ストアに差し替えてください（インターフェースはそのまま使えます）。

エラー時はクライアントに例外の詳細を返しません（内部構成が漏れるため）。
採点に失敗した場合、UIは「採点基準を見る」ボタンから自己採点モードへ切り替わり、
採点基準と模範解答だけを表示します。

### 採点の厳しさについて

システムプロンプトに採点の目安（致命的な観点を落としていれば60点未満、基準の半分程度で
60〜75点、理由まで書けていれば76〜89点、90点以上は基準外の妥当な指摘を含む場合のみ）を
明示していますが、**実データでの検証はまだ行っていません**。
完璧な回答・半分だけの回答・見当違いの回答をそれぞれ通し、スコア分布と
合否の境界（`PASS_SCORE`、`src/lib/grading.ts`）を調整するのが次の作業です。

## 進捗の保存

進捗はブラウザの `localStorage`（キー: `kenpin:progress:v1`）に保存します。
アカウントもサーバーDBも要りません。

読み書きは `src/lib/storage.ts` の `ProgressStore` インターフェースに閉じてあり、
コンポーネントは `localStorage` を直接触りません。複数端末で共有したくなったら、
同じインターフェースを実装したサーバー版に差し替えれば、UI側の変更なしで移行できます。

保存に失敗しても（プライベートブラウジング、容量超過）演習は続行できます。
壊れた値が入っていた場合は空として扱います。

## 設計上の判断

要件定義書で「要検討」とされていた点について、この実装では次のように決めました。

- **永続化はローカル完結**。個人の学習ログという性質上、まずアカウント不要で始め、
  ストレージ層を抽象化して後からサーバー版を足せる形にした。
- **「検印を消す」に確認ダイアログを入れた**。誤タップで全進捗が消えるのを防ぐため、
  消える件数を示したうえで二段階にしている。
- **採点モデルは環境変数で切り替え可能にし、既定を `claude-opus-5` にした**。
  モックの `claude-sonnet-4-6` から変更しているので、コストを優先する場合は
  `ANTHROPIC_MODEL` で切り替えてください。
- **JSONパースの堅牢化は構造化出力で解決した**。文字列の後処理で対処するより、
  そもそも形が保証される経路を使うほうが確実なため。

## 今後の拡張（バックログ）

- **弱点再出題キュー**: AI採点で「抜けていた点」に挙がった観点を記録し、
  同じ観点を持つ設問を優先的に再出題する
- **長文PRレビュー演習**: 数百行規模のAI生成差分を読ませ、優先順位づけをした指摘を書かせる
- **実インシデントベースの問題**: 実際に踏んだ事故を設問として追加する
  （データ構造は変更せずに追加できる）
- **採点の較正**: 複数パターンの回答でスコア分布を検証し、合否の境界を調整する
